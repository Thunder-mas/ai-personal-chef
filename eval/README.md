# RAG 检索评估（eval/）

给"AI 私人厨师"的本地菜谱知识库做一套**可量化的检索评估**——不是凭感觉说"检索还行"，而是用带标准答案的测试集算出硬指标、定位短板、做优化、再用同一套指标**证明优化有效**。这个 **评估 → 优化 → 复测** 的闭环，是生产级 AI 应用和"调包 Demo"的分水岭。

## 文件

| 文件 | 作用 |
|---|---|
| `testset.json` | 评测集：44 条查询，每条标注库中应被召回的相关菜谱（标准答案），覆盖直接点菜 / 近义改写 / 按食材 / 按口味 / 语义 5 类问法 |
| `run_eval.py` | 评估脚本：算命中率/召回率/精确率/MRR，多 top-k 对比，可选 LLM-as-judge，自动出报告 |
| `report.md` | 优化后（当前）评估报告 |
| `report_before.md` | 优化前基线报告，用于对照 |

## 跑

```
python eval/run_eval.py                # 只跑检索指标（离线、不花钱、约 10 秒）
python eval/run_eval.py --ks 1,3,5     # 对比不同 top-k
python eval/run_eval.py --judge        # 额外用大模型评判 Top-1 相关性（需 .env 的 MIMO_API_KEY）
```

## 指标怎么理解

- **Hit@k 命中率**：top-k 里至少有一条相关菜谱的查询占比 —— 最贴近用户体验（"它给我推的有没有用"）。
- **Recall@k 召回率**：该被检回的相关菜谱被检回了多少。
- **Prec@k 精确率**：top-k 里有多少是相关的。k 越大召回越高、精确越低。
- **MRR**：第一条相关结果排名的倒数均值，衡量"好结果排得够不够靠前"。

## ★ 评估 → 优化 → 复测（这是最有价值的部分）

**① 评估发现问题**：在 48 道菜的知识库上跑评测，发现两类语义查询稳定未命中——
- "上火了想吃点降火的" → 检不回 凉拌黄瓜/蒜蓉西兰花 等
- "孩子挑食不爱吃饭想换个花样" → 检不回 可乐鸡翅/糖醋里脊 等

**根因**：纯向量检索只能匹配**字面/语义相近**的文本，而"降火（清热）""适合孩子"这类**营养学/中医/人群属性**根本不在菜谱的菜名、描述、食材里，模型自然映射不到。

**② 针对性优化**：给每道菜补一个结构化的 `attrs` 营养/属性字段（高蛋白、低卡、清热降火、增肌、减脂、三高友好、儿童喜爱…），并把它纳入 `_recipe_to_text` 的检索文本（见 `app/recipe_rag.py`）。

**③ 复测证明有效**（同一知识库、同一评测集，唯一变量=检索文本是否含 attrs）：

| 指标 (k=3) | 优化前 `report_before` | 优化后 `report` | 提升 |
|---|---|---|---|
| **命中率 Hit@3** | 95.5% | **100%** | +4.5pp |
| 召回率 Recall@3 | 68.5% | **70.3%** | +1.8pp |
| 精确率 Prec@3 | 56.8% | **60.6%** | +3.8pp |
| MRR | 0.920 | **0.947** | +0.027 |
| Hit@1 | 88.6% | **90.9%** | +2.3pp |

之前那两条未命中查询，优化后**全部命中**，Top-3 命中率达到 100%。这不是"调包跑通"，而是**用数据驱动的一次真实优化**。

> 注：数据集为自建测试集（44 条），知识库 48 道菜，规模偏小，指标偏高属正常；价值在于**这套可复现的评估-优化方法**，库扩大后同样适用。

## 面试怎么讲（重点）

> "我没有止步于'把 RAG 搭起来'。我建了一套**评测闭环**：44 条带标准答案的测试集，算命中率、召回率、MRR。跑下来发现纯向量检索对'降火''适合孩子'这类**不在文本里的领域概念**有盲区；于是我给知识库补了结构化营养属性元数据并纳入检索文本，**在同一评测集上把 Top-3 命中率从 95.5% 提到 100%、MRR 从 0.92 到 0.95**，那两类盲区查询全部修复。整个过程是**发现问题 → 优化 → 复测证明**，数据驱动、对效果负责。"

这段话直接回答用人单位最关心的：**你能不能把 AI 系统做到能上线、能持续优化、能对效果负责**——正是 RAG / 大模型应用岗位的核心考点。
